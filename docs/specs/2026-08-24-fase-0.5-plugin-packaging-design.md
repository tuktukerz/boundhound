# Design Spec — Phase 0.5: Plugin Packaging

**Date:** 2026-08-24
**Status:** draft
**Prerequisite:** Phase 0 merged.
**Guiding principle:** make Boundhound an installable Claude Code plugin (usable from any project directory) **without weakening any Phase 0 safety guarantee** and **without breaking the 85 passing tests**.

---

## 1. Goal & Non-Goals

### Goal
Package the repo as a Claude Code plugin: a `.claude-plugin/plugin.json` manifest, plugin-relative path resolution for hooks/bin/catalog, and per-user persistent state — so a user can `/plugin install` it once and run `/engagement`, `/mode`, and `omop-exec` from **any** project directory, with the scope-enforcement hook active globally.

### Non-Goals (STRICT)
- ❌ No new attack capability (still Phase 0's tool set: `curl` only).
- ❌ No change to the enforcement *logic* (scope matcher, guard, safety check, audit) — only WHERE it reads code vs data from.
- ❌ Not publishing to a public/large marketplace — distribution is via this repo's own `marketplace.json` (git install).

### Definition of Done
- `plugin.json` valid; plugin installs from the git repo and its skills/commands/hook load.
- Hook fires from a directory OTHER than the repo (proves global activation) and still denies out-of-scope / bypass attempts.
- `engagements/` + audit logs are written under `${CLAUDE_PLUGIN_DATA}` when running as a plugin.
- All existing tests still pass (85+), plus new tests for the path-resolution split.
- README updated (per project rule: README changes ride in this phase's PR).

## 2. Core Change: split "code root" from "data root"

Today every entrypoint uses one `rootDir` (= `CLAUDE_PROJECT_DIR ?? cwd`) for BOTH the tools catalog/templates (code) and `engagements/`+audit (data). A plugin's code lives in a cache dir that is **overwritten on update**, so state must live elsewhere.

**New module `src/paths.mjs`:**
```javascript
import { fileURLToPath } from "node:url"
import { dirname, join } from "node:path"

// Where bundled code lives (tools-catalog.json, engagements/templates/): the
// plugin install dir when running as a plugin, else the repo root (computed
// from this module's own location) when running as a local project.
export function codeRoot() {
  if (process.env.CLAUDE_PLUGIN_ROOT) return process.env.CLAUDE_PLUGIN_ROOT
  return join(dirname(fileURLToPath(import.meta.url)), "..") // src/ -> repo root
}

// Where per-user state lives (engagements/, audit logs): persists across plugin
// updates. Falls back to project dir, then cwd, for local-project use.
export function dataRoot() {
  return process.env.CLAUDE_PLUGIN_DATA
    ?? process.env.CLAUDE_PROJECT_DIR
    ?? process.cwd()
}
```

**Entrypoint changes (behavior-preserving for tests):**
- `runExec(argv, {rootDir, codeDir, dataDir, now, exec})`: internally
  `codeDir = codeDir ?? rootDir ?? codeRoot()`, `dataDir = dataDir ?? rootDir ?? dataRoot()`.
  Catalog reads from `codeDir`; `engagements/`+audit from `dataDir`.
  → Existing tests that pass a single `rootDir` (temp dir holding both catalog and engagements/) keep working unchanged. The CLI entry passes neither and gets the resolvers.
- `createEngagement(name, {rootDir, codeDir, dataDir, containerUp})`: template read from `codeDir`; engagement dir + `.active` written to `dataDir`.
- `hooks/scope-guard.mjs`: `auditHookDeny` uses `dataRoot()` (not `CLAUDE_PROJECT_DIR`) so hook-level DENY audit lands with the engagement state.
- `active-engagement.mjs` / `loadActiveConfig` already take `rootDir` — callers pass `dataDir`.

**Invariant:** the split changes only *locations*, never the deny/allow decision. A regression test must prove `runExec` with separate `codeDir`/`dataDir` behaves identically to the single-`rootDir` case.

## 3. Plugin manifest & layout

**`.claude-plugin/plugin.json`:**
```json
{
  "name": "boundhound",
  "description": "Autonomous pentest agent with enforced, deny-by-default scope safety. Phase 0: safety foundation.",
  "version": "0.1.0",
  "author": { "name": "tuktukerz" },
  "skills": "./.claude/skills/",
  "commands": "./.claude/commands/",
  "hooks": "./hooks/hooks.json"
}
```
*(If the plugin loader rejects `./.claude/...` paths, fall back to top-level `skills/`+`commands/` and update this manifest — the implementer verifies against the loader/docs and picks whichever the loader actually accepts, documenting the choice. Keeping `.claude/` also preserves local-project dev mode; only move if forced.)*

**`hooks/hooks.json`** (plugin hook definition, uses the plugin-root variable):
```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|WebFetch|WebSearch|Write|Edit",
        "hooks": [
          { "type": "command", "command": "node \"${CLAUDE_PLUGIN_ROOT}/hooks/scope-guard.mjs\"" }
        ]
      }
    ]
  }
}
```
`.claude/settings.json` stays as-is for **local-project/dev mode** (`$CLAUDE_PROJECT_DIR`); `hooks/hooks.json` is the **plugin mode** copy (`${CLAUDE_PLUGIN_ROOT}`). Both point at the same script. (Document the two-mode duplication so they don't drift.)

**`.claude-plugin/marketplace.json`** (so the repo is self-installable):
```json
{
  "name": "tuktukerz-marketplace",
  "owner": { "name": "tuktukerz" },
  "plugins": [
    { "name": "boundhound", "source": "./", "description": "Deny-by-default pentest agent safety foundation." }
  ]
}
```

**Install path (README):** `/plugin marketplace add tuktukerz/boundhound` → `/plugin install boundhound@tuktukerz-marketplace`.

## 4. Acceptance Criteria (DoD tests)

| # | Test | Expect |
|---|---|---|
| P1 | `codeRoot()` returns `CLAUDE_PLUGIN_ROOT` when set, else repo root | correct dir |
| P2 | `dataRoot()` prefers `CLAUDE_PLUGIN_DATA` → `CLAUDE_PROJECT_DIR` → cwd | correct precedence |
| P3 | `runExec` with split `codeDir`/`dataDir` (catalog in one, engagements in other) behaves identically to single-`rootDir` (ALLOW in-scope, DENY out-of-scope, audit written to dataDir) | identical decisions |
| P4 | `createEngagement` writes engagement to `dataDir`, reads template from `codeDir` | correct split |
| P5 | All existing Phase 0 tests still green (regression) | 85+ pass (108 pass / 1 skip as of the `${CLAUDE_PLUGIN_DATA}` data-dir fix) |
| P6 | `plugin.json` + `marketplace.json` are valid JSON and declare the expected components | valid |
| E2E | Real hook invocation with `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA` set to temp dirs, run from an unrelated cwd: a denied bypass is blocked (exit 2) AND its DENY line lands in `${CLAUDE_PLUGIN_DATA}/engagements/<name>/audit.log` | blocked + audited in data dir |

## 5. Deferred / Out of scope
- Actually publishing/announcing the plugin — that's a follow-up once installed & smoke-tested.
- Migrating parked Phase 0 findings (guard wrapper-value gap, REPLACE_ME authorization, etc.) — those belong to Phase 1 hardening, not here.
- `${CLAUDE_PLUGIN_DATA}` auto-migration of any pre-existing local `engagements/` — none exist yet in practice; skip.
- **Known limitation — single shared `.active` pointer.** Engagement state
  (including the `.active` pointer file) lives under one shared
  `${CLAUDE_PLUGIN_DATA}` for the whole plugin installation, not per calling
  project. Only one engagement should be treated as active at a time.
  Running different engagements concurrently from different project
  directories against the same installed plugin is **not yet supported** —
  they would share `.active` and could misattribute the audit trail (a run
  kicked off from one project's directory could get logged against another
  project's engagement). This is a known limitation / future-work item
  (e.g. keying state off the calling project, or an explicit engagement
  selector flag), not a defect in the deny-by-default/fail-closed logic
  itself, which still holds correctly for whichever engagement is active.
- **Known limitation — `/engagement` and `/mode` are agent-instruction-
  dependent, not hook-enforced.** Their plugin-mode path resolution (Fix 2,
  final whole-branch review) relies on Claude Code's documented
  content-level substitution of `${CLAUDE_PLUGIN_ROOT}` inside skill/command
  markdown, plus the agent following the written invocation instruction —
  not on `${CLAUDE_PLUGIN_ROOT}` being exported as a real environment
  variable to the agent's Bash tool (per the Claude Code plugins reference,
  that export is limited to hook, MCP, and LSP subprocesses). The
  scope-guard PreToolUse hook has no such dependency: Claude Code registers
  and invokes it directly, so it fires unconditionally regardless of what
  the agent does or doesn't run. Tightening the command surface to the same
  hard-guarantee level as the hook is future work.
- **Fixed — the `${CLAUDE_PLUGIN_DATA}` data-dir gap found by the final
  re-review.** The same "not a real env var to the agent's Bash tool"
  limitation above also applied to `dataRoot()`: `bin/omop-exec.mjs` and
  `bin/omop-engagement.mjs`, run by the agent via Bash in plugin mode, never
  saw `CLAUDE_PLUGIN_DATA` in their own `process.env`, so `dataRoot()` fell
  through to `CLAUDE_PROJECT_DIR`/cwd instead of the plugin's data dir —
  splitting the CLI's engagement state/audit trail from the hook's (which
  does get the env var). Per the plugins reference's substitution table,
  "Skill and agent content" resolves placeholders "anywhere the placeholder
  appears" — the same content-level mechanism `${CLAUDE_PLUGIN_ROOT}` already
  relies on above — so `${CLAUDE_PLUGIN_DATA}` is content-substituted the
  same way. The fix threads it through explicitly: both CLIs now accept a
  `--data-dir <path>` argument (read only in their `isMain` CLI entrypoint,
  passed as the existing `dataDir` option — `runExec`/`createEngagement`'s
  signatures are unchanged), and `.claude/commands/engagement.md` +
  `pentest-mode/SKILL.md` now invoke them with `--data-dir
  "${CLAUDE_PLUGIN_DATA}"` in plugin mode (omitted in dev mode, where the
  existing `CLAUDE_PROJECT_DIR`/cwd fallback is correct). Proven by real
  subprocess E2E in `test/plugin-cli-data-dir.test.mjs`: with
  `CLAUDE_PLUGIN_DATA`/`CLAUDE_PROJECT_DIR` unset and cwd a foreign temp
  dir, `--data-dir <tmp>` routes state/audit to `<tmp>`, and without
  `--data-dir` it falls back to cwd (both cases asserted explicitly). This
  remains agent-instruction-dependent in the same sense as the bullet
  above — it depends on the agent invoking the command/skill text as
  written — not a new hard runtime guarantee.
